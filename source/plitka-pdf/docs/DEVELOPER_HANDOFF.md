# Developer Handoff: Плитка PDF

Дата передачи: 2026-08-24

## Кратко о проекте

«Плитка PDF» — MVP веб-сервиса Vilray Studio для быстрой сборки PDF-документов по плитке и керамограниту: мини-каталогов, коммерческих предложений, прайсов, дилерских презентаций и клиентских подборок.

Коммерческий смысл: дать менеджеру, дилеру или студии быстрый инструмент для подготовки аккуратного PDF без дизайнера и верстальщика. Пользователь берёт готовый сценарий, меняет тексты, изображения, таблицы и контакты, затем скачивает PDF для клиента, дилера или внутренней продажи.

## Текущий технический статус

Проект реализован как статический frontend на `React + Vite + TypeScript`.

Основное приложение в production не требует Node.js-сервера. Node.js нужен локально для разработки, тестов и сборки. Backend есть только для аналитики: PHP API + MySQL на хостинге.

Основные зависимости:

- `react`, `react-dom` — интерфейс.
- `vite` — dev server и production-сборка.
- `typescript` — типизация.
- `html2canvas` + `jspdf` — клиентский PDF-экспорт.
- `lucide-react` — иконки интерфейса.
- `vitest`, `jsdom`, `@testing-library/react` — тесты.
- `eslint`, `typescript-eslint`, `eslint-plugin-react-hooks` — проверка кода.

## Точки входа

Vite собирает несколько HTML-входов:

- `/` — публичный лендинг.
- `/app/` — основной редактор PDF-документов.
- `/admin/analytics/` — админ-панель аналитики.
- `/terms/` — условия сервиса.
- `/privacy/` — политика конфиденциальности.

Настройка multi-page build находится в `vite.config.ts`.

## Как запустить локально

```bash
npm install
npm run dev
```

Обычно Vite открывается на `http://127.0.0.1:5173/`.

Проверка перед передачей или релизом:

```bash
npm run lint
npm run test
npm run build
```

Есть объединённая команда:

```bash
npm run release:check
```

## Структура проекта

Ключевые папки:

- `src/app/` — главная логика редактора: состояние проекта, страницы, история, дизайн, контакты.
- `src/components/` — UI-блоки редактора: холст, верхняя панель, правая панель редактирования, библиотека страниц, модальные окна.
- `src/data/` — шаблоны страниц, пресеты документов, схемы оформления, дефолтные тексты, иконки, промоблоки Vilray.
- `src/styles/` — глобальные стили, темы, layout, стили модальных окон и кабинета.
- `src/landing/` — публичный лендинг.
- `src/legal/` — legal-страницы.
- `src/analytics/` — клиентская отправка событий.
- `src/admin/analytics/` — React-интерфейс админской аналитики.
- `public/api/` — PHP API аналитики.
- `public/brand/` — логотип.
- `public/placeholders/` — демо-изображения, визуальные заглушки, превью шаблонов.
- `docs/` — продуктовая и техническая документация.
- `Каталоги/` — локальная папка с PDF-каталогами-референсами, не является runtime-кодом.
- `outputs/` — результаты визуальных проверок и сканов, рабочие артефакты.
- `dist/` — production-сборка, пересоздаётся командой `npm run build`.

## Что уже реализовано

### Редактор документов

- Desktop-first рабочий интерфейс.
- Создание документа из готового сценария.
- Выбор ориентации A4: вертикально / горизонтально.
- Редактирование зон на странице:
  - текст;
  - изображения;
  - таблицы;
  - списки преимуществ;
  - иконки;
  - разделители;
  - панели/фоновые блоки.
- Выбор зоны кликом на странице и редактирование через правую панель.
- Drag-and-drop загрузка изображений на холст.
- Автосжатие изображений перед сохранением в проект.
- Масштаб холста.
- Полноэкранный просмотр текущей страницы.
- Нижняя лента страниц.
- Добавление, дублирование, удаление и переупорядочивание страниц.
- Undo/redo с ограниченной историей.
- Автосохранение текущего проекта в `localStorage`.
- Предупреждение, если локальное хранилище недоступно или переполнено.

### Локальный кабинет

Кабинет работает без backend, через `localStorage`:

- сохранённые проекты;
- пользовательские шаблоны;
- настройки интерфейса;
- контактный профиль компании/менеджера;
- последние пользовательские цвета;
- настройка показа промоблоков Vilray.

Основные файлы:

- `src/components/modals/LocalDocumentsModal.tsx`;
- `src/utils/storage.ts`;
- `src/app/projectContactOperations.ts`.

### JSON импорт/экспорт

Проект можно выгружать и загружать как JSON.

Файл: `src/utils/jsonImportExport.ts`.

Важно: JSON — это переносимый формат проекта/шаблона между браузерами и устройствами. Основное локальное хранение всё равно находится в `localStorage`.

### PDF-экспорт

PDF собирается на клиенте:

1. страницы рендерятся в DOM;
2. `html2canvas` делает canvas-снимок каждой страницы;
3. `jsPDF` собирает все страницы в один PDF;
4. файл скачивается в браузере.

Файл: `src/utils/pdfExport.ts`.

Перед экспортом открывается модальное окно проверки:

- показывает страницы документа;
- выводит предупреждения по возможным проблемам;
- позволяет сохранить документ как пользовательский шаблон;
- запускает скачивание PDF.

Файл: `src/components/modals/ExportCheckModal.tsx`.

### Аналитика

Клиентская аналитика:

- хранит анонимный ID и session ID в `sessionStorage`;
- складывает события в очередь;
- отправляет пачками на `/api/analytics/batch.php`;
- использует `sendBeacon` перед закрытием страницы;
- режет чувствительные свойства: текст, email, телефон, image src, base64/dataURL и похожие поля.

Файлы:

- `src/analytics/analyticsClient.ts`;
- `src/analytics/projectAnalytics.ts`.

Серверная часть аналитики:

- PHP endpoints в `public/api/analytics/` и `public/api/admin/analytics/`;
- схема MySQL в `docs/analytics_schema.sql`;
- настройка описана в `docs/ANALYTICS_MYSQL_SETUP.md`;
- пример конфига: `public/api/_analytics_config.example.php`;
- реальные доступы должны лежать на хостинге в `_analytics_config.php` и не коммититься.

Админка аналитики:

- `/admin/analytics/`;
- token хранится в браузере под ключом `analytics_admin_token`;
- API требует заголовок `X-Admin-Token`;
- основные вкладки: обзор, воронка, документы, шаблоны, ошибки, события.

## Деплой

Для публикации статической части:

```bash
npm run build
```

На хостинг загружается содержимое `dist/`, а не исходники.

Не загружать публично:

- `src/`;
- `node_modules/`;
- `docs/`;
- `package.json`;
- `package-lock.json`;
- локальные PDF-референсы;
- временные файлы и логи.

PHP/MySQL нужны только если включается серверная аналитика. Без неё редактор и PDF-экспорт остаются рабочими, но события аналитики не будут сохраняться на сервере.

## Важные ограничения MVP

- Редактор рассчитан на desktop. На ширине меньше `1180px` показывается экран «Редактор доступен на компьютере».
- Основное хранение проектов локальное. Если пользователь очистит данные браузера или сменит устройство, проекты пропадут, если заранее не выгружены JSON.
- Нет авторизации пользователей и серверного кабинета.
- Нет общей базы проектов/шаблонов.
- PDF-экспорт зависит от браузерного рендера, веса изображений и ограничений `html2canvas`.
- Большие изображения могут переполнить `localStorage`, несмотря на клиентское сжатие.
- Аналитика анонимная и продуктовая, не CRM.
- PHP analytics config с реальными паролями и токенами не должен попадать в репозиторий.

## Замеченные технические долги

- В `src/app/App.tsx` при дублировании сохранённого проекта есть строка с битой кириллицей в названии копии. Нужно заменить на нормальное `Копия`.
- `DocumentPageStrip` добавляет пустую страницу через `catalog_sample_grid`. Шаблон определён в `src/data/pageTemplates/catalogGrid.ts`, но не подключён в общий список `allTemplateIds` в `src/data/pageTemplates.ts`; сценарий добавления пустой страницы может падать. Нужно либо зарегистрировать шаблон, либо заменить id на актуальный.
- Документы живут в `localStorage`; для реального коммерческого использования нужен backend-слой: аккаунты, облачное хранение, список документов, права доступа.
- Для стабильного PDF в production стоит отдельно прогонять визуальные проверки по ключевым пресетам: `premium_catalog`, `dealer_presentation`, `client_offer`, `price_list`, `selection`.
- В `outputs/` лежат результаты проверок и сканов. Это полезно для разработки, но не runtime-часть продукта.
- Папка `Каталоги/` содержит PDF-референсы и может быть тяжёлой. Её не нужно тащить в production.

## Рекомендуемый порядок доработки

1. Запустить `npm install`, `npm run test`, `npm run build`.
2. Открыть `/app/` и вручную проверить пять видимых пресетов.
3. Исправить явные мелкие баги из раздела технического долга.
4. Принять решение по следующему продуктовым направлению:
   - оставить MVP локальным и усиливать шаблоны/PDF;
   - или делать серверный кабинет с аккаунтами и облачным хранением.
5. Если сервис будет использоваться клиентами регулярно, первым крупным техническим шагом делать backend для проектов и шаблонов, а не расширение текущего `localStorage`.
